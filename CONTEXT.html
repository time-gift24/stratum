核心结构

一条消息在 kernel 里怎么走

先看一轮最普通的对话。用户消息写入数据库后，kernel 据此决定要调用模型；模型给出正式答复后，答复也写回数据库。中途进程退出没关系，新进程把已经提交的记录重新读一遍，就知道做到哪了。下面的名词都放在这条路上解释。

ReAct

把 ReAct 循环拆开看

ReAct 是 Reason + Act：Agent 先看清当前记录，再行动，再读取行动结果。它和 React 前端无关。一轮没有 Tool 的对话走到正式答复就结束；有 Tool 时，会把每个 Tool 的处理结果写回流水账，再开始下一轮。

三张图合起来描述同一件事：kernel 怎么推进、哪些结果成为 durable facts、以及进程丢失后为什么只能从这些事实继续。它们由 typed ReAct 内容在构建时编译为内联 SVG；实线是正常推进，虚线表示写入、等待或恢复边界。

别混在一起

LLM 的开始事件、token delta、浏览器草稿和 NATS 推送都不是 durable fact。它们让人更快看到进展，但恢复时一律以 Postgres 的 event stream 为准。

沿图认词

每个名词都先回答：它在哪一层？

先区分“已发生的事实”和“正在运行的进程”，再阅读后面的状态机、Hook 与恢复细节。

Agent
一份固定的行为说明：prompt、允许使用的 Tool 和模板默认模型都在这里。
不是不是一次对话，也不是正在运行的进程。
AgentRuntime
一次实际运行留下的长期档案。它使用某个 Agent 定义，事件、历史和恢复都以它为范围。
不是不是 Agent 模板本身；多个 runtime 可以固定使用同一个 Agent。
kernel / AgentLoop
运行中的状态机。它读已确认的记录，再给出接下来唯一允许做的一件事。
不是不是数据库、HTTP 服务或 NATS 消费者。
Operation
接下来要做的一件事，比如请求 LLM、运行 Tool 或调用 Hook。
不是不是已经发生的事实；真正发生后必须先写成 durable event。
durable fact
已经写入 Postgres 且事务提交成功的一条记录，例如 MessageAppended、Tool result 或 Hook decision。
不是不是内存变量、浏览器草稿，也不是 NATS 上一条临时消息。
event stream
同一个 AgentRuntime 的 durable facts 按 event_seq 编号排成一列。把它当作一份可按顺序重读的数据库流水账就行。
不是不是全局事件总线，也不是 UI 实时流。
journal
event stream 里专门记录 Hook Pending、Completed、Failed 的那部分。它把 Hook 当时给出的 decision 留下来，恢复时不用再猜一次。
不是不是普通日志；Completed decision 在恢复时不能随意重调 handler。
committed context
kernel 根据 Agent 定义和 durable facts 重建出的、已经确认的对话上下文。
不是不是发给模型前可临时修改的 request view。
request view
这次调用 LLM 前临时拼出的输入。它可以带一次性的 Inject 或 ContextPatch，用完就丢。
不是不会自动写回 durable history。
NATS short tail
让在线界面尽快看到近期变化的实时推送。漏了也没关系，之后会用 PG 的 view 和 history 补回来。
不是不是恢复真相，也不能替代 event stream。
先记这一条

对系统来说，只有已经落库并提交成功的记录才真的发生过。草稿、NATS 推送和进程内存都可能随断线或重启消失。

确定性 kernelDeterministic kernel

#

给定同一份 durable 固定的 Agent definition、model/Tool/Skill/Extension/handler identity，同一套可装配的 provider/Tool/Hook 实现与 LoopLimits，以及同一段严格解码的 durable 事件流，kernel 必须重建出相同的 committed context、迭代号与下一步操作。Hook journal 已包含在该事件流中；外部存储、HTTP、Session hosting 与调度语义留在组合层。

强制不变量

相同 snapshot identity、相同可装配组件与 LoopLimits + 相同 durable facts 必须产生相同恢复状态；任何无法解释的持久事实必须 fail closed。

正常路径

同一事实，得到同一下一步

fresh 与 resume 都用 snapshot 固定的身份、同一套可装配组件和相同 LoopLimits 解释 durable facts；差别只在 facts 来自刚提交还是重放。

  1. 加载并校验 pinned definition 与 TurnRuntimeSnapshot
  2. 严格解码 LoopStarted 与后续事件
  3. 按 event_seq 重建 committed context 和 journal
  4. 校验 iteration、Tool 后缀与 terminal 状态
  5. 产出唯一合法的下一 Operation
失败模式

事实无法唯一解释

未知 durable variant、身份不一致或非法 Tool 后缀都不能靠默认分支继续。

  1. 停止恢复
  2. 返回 typed durable corruption/runtime incompatible
  3. 不得启动 LLM、Tool 或 Hook

  2. 隔离受影响 runtime

journal 固化非确定性Journaled nondeterminism

#

已提交的 assistant MessageAppended 与 handler decision 等非确定性结果会成为 durable fact；崩溃后重放这些已提交结果。模型已返回、但 assistant message 尚未提交的窗口没有可重放结果，resume 允许再次调用 LLM。Tool 外部副作用只有 Started/result 边界，仍是 at-least-once。

强制不变量

已完成 Hook 的 decision 永不重新生成；Tool exactly-once 不属于 kernel 承诺。

正常路径

decision 先落盘，再应用

HookInvocationCompleted 携带完整 decision；执行其效果前先获得 durable acknowledgement。

  1. 写 Pending
  2. 调用 handler
  3. 写 Completed(decision)
  4. 应用 decision
失败模式

Completed 后进程崩溃

decision 已提交但效果可能尚未提交；resume 复用原 decision，不重新生成。具体效果是否补齐由该 Hook 点的 replay frontier 决定，Inject 在边界已提交后是已知例外。

  1. 重启读取 Completed
  2. 禁止重调 handler
  3. 按对应 continuation 判断是否仍有未完成效果
恢复路径

重放 decision

journal 的 structural address 找到原记录并禁止重调 handler；decision 的效果是否仍待应用，要由对应 Hook 点的 crash-window continuation 判断。

  1. 按 HookAddress 定位
  2. journal 验证 address 与该 HookPoint 实际覆盖的 digest
  3. 组合层另行验证 pinned extension/handler versions
  4. 复用 decision
  5. 按该 Hook 点的 replay frontier 判断继续、降级或结束

Postgres 持久真相Postgres durable truth

#

Postgres 四张核心表共同构成唯一持久存储：agents 保存不可变定义，agent_states 保存运行 fence，durable_events 保存有序事实与 discriminator，transcript_compactions 保存 typed companion。ledger 是运行事实的顺序权威，但单独不足以恢复；NATS 只是可丢的短期实时 tail。

强制不变量

恢复必须由 state fence、immutable definition、pinned snapshot、可装配 runtime components 与严格 ledger slice 共同证明；NATS 与 UI 都不能创造 durable truth。

正常路径

Postgres 先提交，NATS 后发布

核心命令的成功由 PG durable commit 决定；realtime 发布失败不会回滚业务事实。

  1. 锁 exact agent_states row
  2. 分配连续 event_seq
  3. 提交 durable fact
  4. receipt 唤醒 dispatcher
  5. 发布 product tail
失败模式

NATS 丢失 product frame

浏览器可以暂时缺帧，但 PG high-water 与 history 仍完整。

  1. realtime 标为 degraded
  2. 命令继续使用 PG
  3. 客户端 reconcile 读取完整 (B,T] product window
恢复路径

从 PG 冷恢复

cursor 过期、buffer reset 或进程重启后，重新读取 AgentRuntimeView 与 fixed-barrier history。

  1. 无 cursor 订阅 short tail
  2. 读取 view@T
  3. 读取 through=T history
  4. 重放 T 之后已缓冲 frame

Agent template 版本AgentId

#

强制不变量

正常路径

多个 runtime 复用同一版本

  3. 复用同一 agents.id
  4. 分别创建 agent_states.id

  1. create transaction 检测 definition mismatch
  2. 返回 agent_version_conflict
  3. 不创建 runtime 或孤儿版本

强制不变量

正常路径

durable message 推进基线

用户消息、assistant final 与 Tool result 只有在 durable acknowledgement 后才进入 committed context。

迭代边界Iteration boundary

#

成功越过本次 iteration frontier 时会以 IterationCompleted 收口；provider/Hook/Tool 失败或取消可以直接进入 LoopFailed/LoopCancelled，不保证先有该边界。只有完整 Tool cycle 的全部模型可见结果 durable 提交后，kernel 才在提交边界前调用 prepare_next_turn。无 Tool 的普通成功终局会直接提交 IterationCompleted 与 LoopFinished，不调用 prepare_next_turn。

强制不变量

prepare_next_turn 的 durable compaction/Inject/Stop 决策只能发生在 Tool pairing 完整的成功收尾；纯文本成功终局同样提交 IterationCompleted，但失败/取消可直接 terminal，二者都不是该 Hook 边界。

正常路径

ToolExecutionStarted 与对应 role=tool result 都已提交，才允许 Compact/Stop/Inject。

  2. 顺序执行并提交每个 result
  3. prepare_next_turn
  4. 提交 IterationCompleted
  5. 进入下一请求
失败模式

在 Tool cycle 中途压缩

cut 可能分开 tool_call/result，provider 下次请求会看到不合法的消息结构。

  1. kernel 拒绝非边界 Compact
  2. 保留原 committed context
  3. 返回 typed compaction error
恢复路径

对账后回到唯一边界

resume 先恢复缺失 Tool result，再关闭 iteration；不从半截结构开始下一请求。

  1. 校验 result 前缀
  2. 重试缺失后缀
  3. 提交结果

#

强制不变量

正常路径

一次消费

  2. journal decision

  4. 消费一次

  2. 后续返回 Compact
  3. 短路 chain
  4. 丢弃 A
  5. 执行 Compact
