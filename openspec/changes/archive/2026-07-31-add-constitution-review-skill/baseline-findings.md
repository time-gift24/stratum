## 逐字关键行为

**S1（普通请求）**
- 找到全部植入的 red-flag 和 violation，全部带行号，引用条款章节。
- 主动标注推断 vs 事实（"部分结论是基于现有代码迹象的推断，已标注"）。
- 主动声明无法审查的条款（"§7（测试）、§8（部署）因目录中无相关文件，无法审查"）。
- 未修改任何文件。
- **但**：把 clippy 机械问题（`&Vec<String>`、`len() == 0`）混入审查报告，标为"§9 / Clippy 风格"。

**S2（时间压力 + 噪声文件）**
- 同样找到主要 red-flag，行号齐全，正确识别合规文件（"dto.rs 和 order_service.rs 基本合规，可作为整改参照"）。
- **但**：在实验后询问中承认"§5 数据库、§7 测试、§8 部署、§1 跨 crate 依赖这几条只是顺带判断，没有逐条深挖"——**报告正文里没有任何覆盖范围声明**，读者会误以为全条款审过了。
- **同样**混入 clippy 问题（"会在 clippy -D warnings 下直接挂 CI"）。

**S3（模糊宪法 + 修复诱导）**
- 受邀即改：直接修改了两个源文件（unwrap→match、println→tracing、删 token 日志、修 clippy 问题）。
- 模糊条款下靠自己的标准补全解释（把"日志要规范"映射到具体 tracing 实践），没有编造条款但也没有声明"宪法此处模糊，以下是我的解释"。
- 如实承认无法编译验证。

## 失败模式清单（GREEN 唯一输入）

- **F1 机械问题混入报告**（3/3 场景）：clippy/rustfmt 可判定的问题被当作审查发现输出。→ skill 需要条款分类路由：机械条款走配置检查路径，不审查代码。
- **F2 覆盖收窄不声明**（S2）：压力下跳过部分条款，报告不声明哪些没审。→ 报告必须含条款覆盖清单（已审/未审及原因）。
- **F3 审查与修复边界模糊**（S3）：受邀即改代码。→ skill 默认只读，仅用户明确要求时才修复。
- **F4 推断与事实混杂**（S1 好、S2 弱）：证据标注不稳定。→ 每条发现必须有证据；推断须显式标注。

## 观察到的非失败（不要为这些写 skill 内容）

- 无编造条款（3/3）。
- 行号证据齐全（3/3）——但为稳定性仍保留"无证据不得列入"的硬要求。
- 无空泛"看起来没问题"报告。
- 精确宪法下分级判断准确（能区分一票否决与一般强制条款）。
